# Local development character resume

This opt-in foundation accepts local loopback clients and two to four server-configured profiles. It is disabled in the ordinary merchant package and in Shipping. Use a separate reviewed test-map copy without the standalone progression actor, PC0 area loop or legacy swing driver; supply the original weapon assets and required pawn contract before enabling the foundation.

A fresh connection receives an unused profile and a random ticket issued by the server. Logout releases the connection while retaining that profile's ticket and progression model. A reconnect presents `?JadeboundResume=<issued-ticket>` in its loopback travel URL. Rejoining in a different order retains the original profile. Bare character IDs, unknown tickets, malformed or duplicate options, and tickets already active or pending are refused. Refusal never falls back to a different profile. A fresh join cannot claim a disconnected profile.

The owning client stores its ticket in `Saved/JadeboundDevelopmentResume/<server-session>_<character>.ini`. Saved files are ignored by Git. Keep ticket values out of source, screenshots, shared logs and reports. URL travel and engine logging are local development mechanisms; this is a bearer ticket, without production authentication or transport protection. An existing conflicting receipt is preserved and reported without its contents. A receipt write failure leaves the server reservation intact and needs investigation before relying on a reconnect.

Tickets last for this running server session. Restarting the server invalidates them; durable account-to-character identity and server-restart recovery remain separate unfinished work. Do not describe a reconnect test here as MMO capacity, account security or persistence service readiness. Development profiles are not an account service.

The [native player life slice](NativePlayerLife.md) retains health, death generation and the revive deadline on that same server character model. Rebinding a pawn cannot reset it to alive. This state is runtime-only; progression journals do not yet persist health/death across a server restart. A synthetic pawn-rebind test does not qualify ticket delivery or client reconnect ordering.

Qualification must use independent clients: give A and B distinguishable inventory/currency/quest state; disconnect both; rejoin B before A with their own receipts; verify retained state and visible equipment. Reject wrong, duplicate and missing tickets after the roster is bound. Repeat with four clients, an interrupted first admission, a failed receipt write, pending-save retry, and a server restart. Portable tests and an Unreal compile do not establish these gameplay/transport results.

Portable C++17 tests live under `Tests/Portable`, outside UnrealBuildTool's source tree. Build each test as its own executable with MSVC `/std:c++17 /permissive- /EHsc /W4 /WX`; the registry test deliberately replaces allocation functions to inject failures and must never be linked into the game. It checks full state preservation on failures, reversed reconnect order, retained reservations and cancellation. The options test checks the actual production parser and its admission contract.
